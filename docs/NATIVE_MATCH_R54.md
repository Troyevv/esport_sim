# R5.4. Эталон подробного BO1 и первый компонент C++20

## Состояние переноса

В этой ветке C++ владеет геометрией поиска NAV-поверхности. Стенд подставляет её в подробный BO1. Игра продолжает исполнять подробный тик в Python. Следующие критерии R5.4 остаются открытыми: владение состоянием матча в C++, полный перенос тика, измерение двух самостоятельных ядер, интеграционная приёмка и переключение. Быстрый расчёт в `round_sim.py` живёт отдельно.

## Аудит и границы владения

| Участок | Путь исполнения и требования к переносу |
|---|---|
| Вход в матч | `match.initial` получает изолированный домен и заявки через `database.match_input`. `series.next_map` задаёт карту, seed и стартовую сторону. Версии карты, правил, схемы сохранения и данных имеют разный смысл. |
| Геометрия | `cs2_navigation` работает в Hammer XYZ. `cs2_maps.Map` переводит координаты в единицы симуляции, кеширует поиск и различает NAV-портал и физически проходимый путь. Два входа в один полигон могут вести к разным результатам обхода препятствия. `cs2_profiles` привязывает именованные позиции, `cs2_sites` проверяет трёхмерные объёмы. |
| Коллизии и восприятие | `cs2_collision` сочетает треугольники и аналитические примитивы с разными масками. `cs2_rays` уже вызывает Embree 4 SSE2 из Python через ctypes. Порт должен воспроизводить порядок разрешения совпадающих граней. В `match_ai` и `cs2_play` слух даёт наблюдение с датой, передача по радио добавляет задержку. |
| Порядок тика | `match.advance` обрабатывает freeze/result, сортирует агентов по стартующей команде и слоту, применяет эффекты, обновляет восприятие, запускает решения капитана и агентов и разрешает действия. RNG принадлежит агентам. Число и порядок обращений к 32-разрядному LCG входят в эталон вместе с его состоянием. |
| Планы и исполнители | `cs2_openings`, `cs2_defense`, `cs2_retake`, `cs2_intel`, `cs2_play` и `match_ai` читают разные представления информации. `tactic_library` хранит версии досок, `tactics` валидирует команды, `tactic_execution` двигает курсор исполнителя, `tactic_preview` вызывает симуляцию. Версия доски и прогресс пяти маршрутов нужны при восстановлении. |
| Правила и журнал | `match_performance` применяет навыки и подготовку. `match_inventory`, `cs2_economy`, `match_rules`, `match_events` и `match_score` связывают покупки, снаряжение, урон, серию поражений и смену сторон с очередностью событий. Оценивать паритет по одному счёту недостаточно. |
| Сохранения и клиенты | `Store.tick` внутри транзакции читает снимок, исполняет пакет шагов до паузы или конца карты, записывает состояние и переносит закрытые раунды в `round_log`. После rollback обработчик должен видеть состояние до операции. `match.project` формирует представления наблюдателя и сторон. Клиент получает разрешённый снимок и образцы движения. |
| Серии и карьера | `series`, `registrations`, `competitions`, `training`, `career` и SQLite сохраняют заявки, veto, регламент, подготовку, результаты BO1/3/5, пракки и архив. Эти потребители образуют внешнюю границу симуляции. |

### Контракт реализованного модуля

`backend._match_native.NAV_API_VERSION == 1`. Конструктор `NavSurfaces([(area_id, corners), ...])` принимает полигоны в Hammer XYZ и создаёт собственный неизменяемый индекс на время жизни карты. `locate_many(points, max_vertical)` возвращает список ID или `None` в порядке запросов. Равенство высот разрешается по меньшему ID. Конвертация в собственные массивы завершается под GIL. Обработка массива и построение индекса освобождают GIL. Несколько потоков могут запрашивать один индекс. Повреждённая геометрия вызывает исключение. Пакетный API проверен также отдельно от Python под ASan/LSan и UBSan.

### Контракт следующего этапа

Границу матча следует проводить вокруг пакета тиков. Создание получает ID и версии ресурсов, составы, seed, подготовку и доски. Восстановление получает версию ядра, правил, RNG, карты и контрольную точку. Один объект владеет всеми изменяемыми данными десяти агентов, планами, очередями, журналом и игровым временем. Команды проверяются между пакетами. Пакет возвращает число фактически пройденных шагов, причину остановки, новые события и запрошенную проекцию. Для параллельных клиентов сериализация изменений должна охватывать ревизию сервера и commit SQLite. Экспорт контрольной точки требуется до публикации новой ревизии, при отказе записи возвращается предыдущее состояние. Эти операции над матчем предстоит реализовать и проверить.

## Методика

Исходник Python — `d78ebe5`, Linux x86-64, AMD EPYC 9V45, CPython 3.12.14, NumPy 2.5.5, embreex 4.4.0.post1. Для каждой карты использован отдельный процесс с `OPENBLAS_NUM_THREADS=1`. Девять полных BO1 используют одну пару составов из ноябрьской базы, seed 41000, штатные планы, на нулевом тике — запрос перерыва и возобновление. Зафиксированы хеш доменного входа, правила `cs2-bo1.20`, BuildID 26879581 и checkpoint v7.

BO1 включает холодную инициализацию матча, команды, тики и сбор контрольных данных. Загрузка базы сцены предшествует таймеру. Среднее, P95 и P99 по одному вызову `match.advance` включают все фазы, в том числе фризтайм. Пик RSS относится ко всему процессу и может включать разбор базы. В парном прогоне используется Python с C++-поиском NAV и восстановлением из JSON на тике 150. Wall и CPU даны отдельно. ### Профиль и стоимость границы

В отдельном прогоне Nuke под cProfile из 29,97 с суммарного времени `match.advance` поиск физического пути `Map._path` занял 18,24 с с учётом вложенных вызовов, 11,16 с собственного времени за 6 094 вызова. Обычный `Navigation.route` занял 3,30 с суммарно. `TriangleScene.first_many` занял 2,00 с. Эти числа перекрываются. Следующий приоритет переноса — физический путь с входной точкой портала, коллизиями и локальным обходом препятствий.

На 256 центрах NAV Nuke прямой Python-поиск занял 6 216 мкс, пакет C++ — 61,61 мкс, те же запросы через 256 отдельных вызовов — 123,61 мкс. Пустой вызов с конвертацией результата и освобождением GIL занял 0,169 мкс. Указаны медианы пяти серий. Приёмочный стенд подставляет поиск в существующий Python-код скалярно, чтобы проверить эквивалентность в настоящем матче. Для игрового C++-тика этот адаптер не предназначен.

### Повторение

Нужны C++20 и Python 3.12 с заголовками разработки. На Windows используется x64 Visual Studio Build Tools. В окружении разработчика выполните команды из корня репозитория.

```sh
python -m pip install -r requirements-test.txt -r requirements-native.txt
python -m tools.build_native
python -m pytest -q tests/test_native_navigation.py
python -m backend.map_install
python -m tools.measure_native_navigation --map de_nuke
python -m tools.measure_detailed_match --map de_nuke --out build/reference --expect tests/fixtures/r54/reference.json
python -m tools.measure_detailed_match --map de_nuke --out build/paired --native-nav --checkpoint tests/fixtures/r54/de_nuke.checkpoint.json.gz --expect tests/fixtures/r54/reference.json
```

Для остальных карт подставьте её ID и одноимённый checkpoint. Для профиля используйте `python -m cProfile -o build/nuke.prof -m tools.measure_detailed_match --map de_nuke --out build/profile`. Массовые матчи запускаются вручную. CI собирает модуль под Linux и Windows, проверяет геометрию и владение памятью. Штатный workflow Windows включает .pyd в дистрибутив, запускает EXE на чистом Server Core и проверяет повторный запуск BAT/EXE с общим профилем.
