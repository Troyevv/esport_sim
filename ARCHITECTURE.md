# Техническая архитектура

**Статус.** Рабочий проект реализации. Поддержка мобильных устройств с R0 согласована. В R0 реализован стенд движения и восприятия. Имена модулей, сущностей и контрактов ниже описывают целевую структуру, для следующих этапов. В R0 независимое ядро находится в `backend/engine.py`, владение состоянием и атомарные команды — в `backend/store.py`, HTTP и WebSocket — в `backend/server.py`. Интерфейс расположен в `frontend/src/`.

Продуктовые требования находятся в [GAME_DESIGN.md](GAME_DESIGN.md), поведение матчей и редактора — в [MATCH_SIMULATION.md](MATCH_SIMULATION.md), последовательность реализации — в [ROADMAP.md](ROADMAP.md). Неоднозначности и решения, требующие дальнейшего уточнения, собраны в [DECISIONS.md](DECISIONS.md). Проверяемые внешние правила и источники данных — в [SOURCES.md](SOURCES.md).

## 1. Границы системы

Игра предназначена для одного пользователя и одной активной карьеры за раз. Несколько независимых карьер можно хранить и открывать по очереди. Несколько подключений принадлежат одному менеджеру и используют общее состояние мира и общие сохранения. Игровые аккаунты, лобби и мультиплеер исключены.

Домашний ПК запускает сервер симуляции и хранит данные. Один веб-клиент работает в браузерах ПК, смартфонов и планшетов с R0. Поддерживаются доступ на самом ПК, подключение по локальной сети и защищённое удалённое подключение. Сервер — единственный источник истины. Мобильному клиенту нужна связь с ним, автономный режим не требуется. Сам ПК и локальная сеть работают без интернета при установленной игре и подготовленной базе. Импорт обновлений базы и текстовая LLM-интеграция остаются необязательными операциями.

Основные инженерные решения:

- Один модульный backend и одна точка изменения состояния активной карьеры.
- Независимое от интерфейса ядро матча, пригодное для запуска без графики.
- Одно ядро для наблюдаемых, ускоренных и фоновых официальных матчей.
- Отдельная облегчённая модель любительского FACEIT, явно отличимая от официального матча.
- Стабильные идентификаторы, версионируемые правила и воспроизводимость результатов.
- Тексты, рейтинги, статистика и визуализация получают данные из событий игры.

Микросервисы, отдельный брокер сообщений и серверная СУБД не требуются для исходной задачи. Усложнять эту схему можно только ради выявленного ограничения.

## 2. Рабочий технологический стек

Зависимости R0 зафиксированы. Первый замер относится к движению и восприятию на одной тестовой карте.

| Компонент | Рабочий выбор | Ответственность |
|---|---|---|
| Интерфейс | React + TypeScript | Экраны управления, формы, таблицы, карточки, календарь |
| Карта матча и тактическая доска | PixiJS | Отрисовка геометрии и маркеров, интерактивные инструменты, анимация представления |
| Сервер на домашнем ПК | Python + FastAPI | Команды пользователя, запросы представлений, управление жизненным циклом карьеры |
| Симуляция | Независимые Python-модули | Правила матчей и мира, NPC, расчёты и события |
| Постоянное хранение | SQLite | Карьеры, история, сохранения, индексы и версии |
| Передача обновлений | HTTP + WebSocket | HTTP для команд и запросов; WebSocket для событий, кадров и прогресса |
| Проверки | pytest, инструменты TypeScript, Playwright | Инварианты ядра, контракты, интеграционные сценарии и интерфейс |
| Мобильная упаковка | Последующий Capacitor для Android и iOS | Нативная оболочка общего frontend, который продолжает работать с домашним сервером |
| Запуск в Windows x64 | EsportSim.exe, PyInstaller one-folder | Локальный FastAPI с упакованным Python и готовым frontend. Интерфейс открывается в системном браузере |

С R0 адрес сервера настраивается вне доменных компонентов клиента. UI обращается к общему API и не зависит от фиксированного `localhost`, прямого доступа к SQLite или файловой системе ПК. Подготовка к Capacitor включает учёт жизненного цикла клиента, безопасных областей экрана и разрешённых origin браузера и будущей оболочки. Сборки Android и iOS относятся к последующему этапу. При переходе приложения в фон и обратно применяется тот же контракт восстановления соединения и состояния.

FastAPI документирует поддержку WebSocket; SQLite документирует применение в локальных приложениях и в качестве формата файла приложения. Это основания для предлагаемого выбора, а не доказательство достаточной производительности нашей симуляции: [FastAPI WebSockets](https://fastapi.tiangolo.com/advanced/websockets/), [SQLite: подходящие сценарии](https://www.sqlite.org/whentouse.html).

Для R0 выбраны Python 3.12, Node.js 24, npm и Vite. Версии фиксируются в манифестах и lock-файлах; нельзя писать в документации выдуманные команды запуска до появления соответствующих файлов. Обновление зависимостей не должно незаметно менять поведение симуляции.

## 3. Разделение ответственности

| Модуль | Чем владеет | Чего не делает |
|---|---|---|
| `match_engine` | Раунды, игроки на карте, восприятие, решения, физические действия, экономика матча | Не импортирует React, PixiJS, FastAPI, SQLite или LLM-клиент |
| `world` | Игровое время, расписание событий, развитие и автономные действия мира | Не привязывает развитие карьеры к реальному времени компьютера |
| `competitions` | Турниры, заявки, регламенты, матчи и продвижение по стадиям | Не начисляет произвольные «очки Valve» |
| `rankings` | Адаптер выбранной версии VRS, история рейтингов, расчёт игровых оценок | Не подменяет результат матча рейтингом силы |
| `rosters_contracts` | Составы, регистрации, переходы, контрактные обязательства | Не меняет задним числом состав уже сыгранного матча |
| `training_scouting` | Развитие, практика, изученность, отчёты и давность наблюдений | Не отправляет истинный потенциал чужого игрока в UI |
| `people_club` | Владелец, персонал, доверие, отношения, обещания, инфраструктура | Не сводит все отношения к единой случайной шкале |
| `finance` | Бюджеты, платежи, призовые и журнал операций | Не начисляет доход повторно из-за повторной доставки события |
| `amateur_scene` | Любительские матчи, Elo, появление и развитие талантов | Не выдаёт агрегированную симуляцию FACEIT за полный матч ядра |
| `media` | Новостные поводы, интервью, награды и опубликованный текст | Не создаёт факты мира из сгенерированной реплики |
| `data_packs` | Импорт, проверка и происхождение исходной базы | Не обновляет существующую карьеру данными внешнего мира |
| `persistence` | Транзакции, схемы БД, сохранения, миграции, архивы матчей | Не определяет игровой баланс |
| `application/api` | Прикладные операции и разрешённые пользователю представления | Не содержит вторую реализацию игровых правил |
| `frontend` | Ввод, отображение и локальное состояние интерфейса | Не определяет результат попадания, трансфера или интервью |

Это логические границы внутри одного приложения. Не нужно создавать отдельный процесс, репозиторий или универсальный плагин для каждой строки таблицы.

## 5. Сущности и идентичность

Идентификаторы не выводятся из никнейма, названия организации или текущего состава. Переименование не создаёт нового человека, а смена пятёрки не переписывает исторические результаты организации.

| Сущность | Значимые данные и связи |
|---|---|
| `Career` | Игровая дата, seed, состояние генераторов случайности, версии и настройки карьеры |
| `Person / Player / Staff / Manager / Owner` | Стабильная личность, профиль, роли, навыки, контракты, отношения |
| `Organization` | Идентичность клуба, владелец, бюджеты, инфраструктура, составы и академия |
| `Roster / RosterMembership` | Участники и интервалы членства; отдельно регистрация на событие |
| `CompetitionEdition / Stage / Match / MapResult` | Конкретный турнир, стадии, формат серии и фактические результаты |
| `Ruleset / MapGeometry / MapPool` | Версионированные правила симуляции, геометрия и активные карты |
| `Tactic / TacticRevision / Familiarity` | План, версия плана, назначение ролей, освоение конкретным составом |
| `Contract / Negotiation / Promise` | Стороны, условия, сроки и исполнимые обязательства |
| `TrainingSession / ScoutingAssignment / Observation` | Выполненные занятия и наблюдения с датой и источником |
| `KnowledgeProfile / ScoutReport` | Известные менеджеру диапазоны, уверенность и давность информации |
| `FinancialEntry` | Сумма в минимальных единицах валюты, назначение, стороны, дата, источник |
| `Relationship / Memory / Interview / NewsItem` | Направленные отношения, значимые события, текст и основание последствий |
| `RankingSnapshot` | Версия модели, дата расчёта, входные данные и результаты |
| `ScheduledEvent / DomainEvent` | Запланированное действие и уже совершившийся факт с порядком обработки |

Организация, зарегистрированная пятёрка, историческое ядро состава для рейтинга и команда на конкретной карте — разные понятия. Точное сопоставление с VRS определяет адаптер официальной модели; его нельзя заменять постоянным рейтингом на `organization_id`.

Для навыков и отображаемого общего рейтинга действует продуктовая шкала 0–100. Формулы OVR игрока, OVR команды и влияние штаба являются параметрами баланса. Не следует произвольно усреднять всё в одну величину и использовать её повторно как множитель каждого действия: это создаст скрытый двойной учёт одного преимущества.

## 6. Команды, изменения состояния и события

Пользовательский ввод проходит последовательность: команда → проверка текущего контекста → изменение предметного состояния → запись события → обновление представлений. Событие описывает уже совершившийся факт. Ошибка или отказ не должны оставлять частично применённое действие.

Команда изменения состояния содержит устойчивый идентификатор (`command_id`), идентификатор активного сценария или карьеры, ожидаемую ревизию, тип и данные. Сервер последовательно обрабатывает команды всех клиентов в одной точке записи. Для новой команды он проверяет ревизию затрагиваемого состояния и предметные условия на момент применения. Номер визуального кадра не используется как ревизия команды. Две конфликтующие команды из одной ревизии не могут перезаписать друг друга. При отклонении устаревшей команды клиент обновляет представление, показывает причину и оставляет решение о новом действии менеджеру.

При повторе той же команды сервер сначала ищет её сохранённый результат, затем проверяет ревизию для незнакомого идентификатора. Он возвращает исходный результат повтора без повторного эффекта. Повторное использование идентификатора с другими данными отклоняется. Эффект, события и сведения для распознавания повтора фиксируются атомарно до подтверждения клиенту. После потери ответа клиент сверяет исход команды по её идентификатору. Клиент удерживает исходные идентификатор и данные до разрешения неопределённого результата. При безопасной повторной отправке сохраняется исходная ревизия, чтобы запоздавшая команда прошла те же проверки допустимости.

Примеры прикладных команд: запросить продвижение времени, назначить тренировку, сделать предложение по контракту, запросить тайм-аут, выбрать тактику в разрешённом перерыве. Это перечень контрактов, а не готовые пути API.

Каждая запись события содержит стабильный идентификатор, игровое время, последовательный номер, тип, участников, версию схемы и ссылку на причину. Факты матча дополнительно используют `match_id`, карту, раунд и тик.

Изменение состояния и записи, необходимые для его корректного восстановления, фиксируются согласованно. Для критичных действий — контрактов, финансов, итогов турнира, переходов времени — это одна транзакция с явными уникальными ключами. Повторная обработка результата матча не удваивает призовые, опыт, статистику или эффект для VRS.

Полное event sourcing всего приложения не является обязательным. Достаточно сохраняемого состояния, значимого журнала событий и специализированного архива матча. Не нужно превращать каждое движение маркера в отдельную строку общеигровой истории.

## 7. Ядро матча

### 7.1. Детерминированный вход

Полный вход матча включает составы и доступные навыки, подготовку и состояние игроков, тактики, геометрию, правила, матчевую регистрацию, исходную экономику и seed. Во время матча к нему добавляются разрешённые команды с точным моментом применения.

Ядро использует собственное модельное время и фиксированный шаг расчёта. Частоту шага выбирают после измерений точности и производительности; она не объявляется заранее эквивалентной частоте реального CS. В R0 модельный шаг равен 100 мс. Сервер присылает проекции независимо от обновления экрана. При ускорении пакет включает видимые подтверждённые позиции и направления на промежуточных тиках.

Радар PixiJS обновляется на каждом доступном обновлении экрана. Сетевой обработчик передаёт в буфер каждый подтверждённый снимок до обновления React. Единые часы показа идут по модельным интервалам. Запас начинается с 200 мс и растёт при джиттере до 450 мс. При устойчивом потоке и остатке менее 180 мс часы показа плавно замедляются до 32% базовой скорости. Длина уже полученного пути и его повороты сохраняются. Когда данных больше нет, маркер остаётся на последней подтверждённой позиции. При изменении скорости уже полученные участки сохраняют свою длительность. Пауза, загрузка, сброс и переподключение устанавливают актуальную проекцию.

На прямой используется линейная интерполяция. Для поворота нужны соседние подтверждённые точки. Кривая проходит через серверные позиции и допускается только когда прямоугольник, охватывающий её контрольные точки, свободен от стен. Иначе маркер следует разрешённому прямому отрезку или остаётся на последней позиции до следующего узла. Указатель направления поворачивается по кратчайшей дуге с ограничением угловой скорости. Скрытые контакты удаляются сразу. Если подписчик пропустил сообщения, сервер может дополнить проекцию непрерывно наблюдаемыми позами из последних шести пакетов той же скорости и мира. Буфер хранится в памяти. Выбор использует положение нарисованного маркера, а команды, восприятие агентов и сохранения используют серверное состояние.

При одинаковом входе, версиях, порядке команд и состоянии генераторов результат должен воспроизводиться. Для этого нужны стабильный порядок обхода объектов, определённый порядок разрешения одновременных событий и управляемые потоки случайности. В ядре запрещены зависимость от FPS, текущего времени ОС и случайный порядок завершения фоновых задач.

Изменение скорости просмотра меняет число вычисленных шагов за реальную секунду и режим доставки кадров. Оно не меняет вероятность попадания, качество решений, итоговую статистику или исход матча. Результат возникает из действий агентов; заранее выбранный счёт с анимацией поверх него недопустим.

В R1 модуль `backend.match` исполняет профиль `depo-bo1.1` фиксированными шагами того же размера. Сервер выбирает движок по версии мира. Снимок R0 продолжает работать с ядром R0. Снимок BO1 содержит фазу, дедлайны, активное действие с C4, эффекты, очередь сообщений, намерения, знания, генераторы и бюджет тайм-аутов. При переходе к следующему раунду SQLite сохраняет журнал предыдущего по SHA-256 в той же транзакции, что и контрольное состояние. Сохранения разделяют записи истории по содержимому. Публичные проекции включают итоги раундов, а для наблюдения 1–8× сервер передаёт допустимые промежуточные позы. Начало нового раунда сбрасывает интерполяцию между раундами.

### 7.2. Слои состояния

Необходимо разделить:

1. **Истинное состояние:** геометрия, позиции, здоровье, снаряды, дым, бомба и экономика.
2. **Знания агента:** что он видел, слышал, получил от союзников, когда и с какой уверенностью.
3. **Решение агента:** намерение, выбранный план, цель, оценка риска и следующая допустимая команда.
4. **Представление наблюдателя:** разрешённые текущему режиму данные для радара и статистики.

Игроки и IGL принимают решения по своим знаниям, а не по полной карте. Потерянный из видимости противник оставляет устаревающее наблюдение, не постоянную привязку к живым координатам. Сообщение союзника должно иметь источник и модель доставки; капитан не получает скрытую информацию автоматически.

Просмотр полной карты человеком и знания агентов — независимы. Допуск полного обзора в матче своей команды и его влияние на честность тренерских решений остаются вопросом режима наблюдения в `DECISIONS.md`; техническая возможность не устанавливает продуктовую политику.

### 7.3. Геометрия и действия

Изображение радара не заменяет модель пространства. Геометрия хранит проходимые области, препятствия, покрытия видимости, позиции установки бомбы, точки появления и связи навигации. Системы видимости, движения и бросков используют согласованную систему координат и одну версию геометрии.

Детализация движения, стрельбы и гранат должна позволять объяснить исход раунда действиями игроков. Степень физической точности определяется измеримыми сценариями, а не заявлением о полном копировании движка CS. Для карт с несколькими этажами потребуется явное представление уровней и связей: нельзя считать все пересекающиеся линии проходами.

Набор состояний раунда и карты должен различать подготовку/закупку, активный раунд, установленную бомбу, завершение раунда, смену стороны, разрешённые перерывы и завершение карты/серии. Время, победные условия и экономика читаются из выбранного правилом набора, а не дублируются в UI.

### 7.4. Тактика и управление тренера

В R2 библиотека тактик и освоение редакций находятся в отдельных таблицах профиля. Сервер проверяет версию плана внутри транзакции команды. BO1 закрепляет копию назначенной редакции в контрольной точке версии 3. Счётчики шагов живут у исполнителей, навигация и разрешение намерений используют обычный матчевый цикл. Спарринг создаёт отдельный мир на том же ядре. [Данные и переход со старых сохранений](docs/TACTICS.md)

Редактор сохраняет предметный план: карта и её версия, сторона, исполнители или роли, маршруты, позиции, направления контроля, ожидания и действия. Пользователь не обязан составлять программу или граф логических операторов. Внутренняя логика исполнения и адаптации остаётся ответственностью ИИ.

План проверяется по геометрии, составу и доступному снаряжению. Предпросмотр и реальное исполнение должны использовать общие определения действий и навигации. Предпросмотр не гарантирует, что противник и исполнители позволят повторить маршрут без изменений.

При изменении состава назначение ролей перепроверяется; при изменении геометрии устаревшие действия обнаруживаются и объясняются пользователю. Необходимо сохранять версии тактик, чтобы отчёты об эффективности относились к тому плану, который реально использовался.

Во время матча игровая команда тренера принимается только в разрешённом тактическом тайм-ауте. Проверка находится в ядре/прикладном слое, а не только в доступности кнопки. Обычная зрительская пауза, reconnect, быстрая симуляция и открытие статистики не дают права на колл.

Пользовательское требование — **три тактических тайм-аута за матч**. Нельзя незаметно заменить его тремя на карту. Значение слова «матч», продолжительность, овертаймы и привязка к реальному регламенту разобраны в решении D-01 из `DECISIONS.md`; модель хранит лимит и область его действия явно. Первый сценарий BO1 на одной карте позволяет реализовать лимит без этой неоднозначности, но не решает её за пользователя для BO3/BO5. Запрос перерыва и фактический вход в него — разные события: середина активного раунда не становится произвольной точкой остановки игровых действий.

Обратная связь во время перерыва выводится из доступных персонажам фактов: неудачных выходов, разменов, повторений соперника, экономики, конфликтов. Факт события и интерпретация игрока хранятся отдельно; ошибочная оценка персонажа не меняет саму историю матча.

## 8. Время мира и фоновые расчёты

Основное время стоит, пока менеджер работает с интерфейсом. «Продолжить» обрабатывает очередь до следующей точки остановки, выбранной даты или события, требующего решения. Для событий с одинаковым временем заранее задаётся устойчивый порядок по типу/приоритету и идентификатору.

Одна служба карьеры последовательно применяет изменения мира. Для тяжёлых независимых матчей можно использовать процессы-работники: они получают неизменяемый вход и возвращают результат. Работник не изменяет SQLite и другие объекты мира самостоятельно. Применение результатов происходит в определённом модельном порядке, независимо от того, какой процесс закончил раньше.

Распараллеливаются только действительно независимые задачи. Следующую стадию турнира нельзя рассчитывать до фиксации результатов предыдущей; один игрок не может одновременно участвовать в несовместимых событиях. Отмена продвижения времени останавливает работу на согласованной границе и не оставляет половину тура применённой без учёта остальных событий.

Карьеры, трансферы, состояния игроков, развитие и любительская сцена рассчитываются с подходящей частотой события, а не на каждом тике матча. Облегчённая модель FACEIT имеет отдельную версию, управляемую случайность и сохраняемые результаты. Она не создаёт VRS-матчи и не используется для скрытого упрощения официальной сцены.

Масштаб обсуждавшихся баз — ориентир для последующих измерений. Нельзя обещать тысячи полноценных матчей за секунду или конкретное число десятилетий истории без профилирования.

## 9. Версии правил, базы и VRS

Версии необходимо различать, поскольку их жизненные циклы не совпадают:

| Версия | Что фиксирует |
|---|---|
| `save_schema_version` | Структуру сохранения и путь миграции |
| `simulation_version` | Алгоритмы ядра, порядок расчётов и RNG-контракт |
| `dataset_version` | Исходную реальную базу, дату среза и происхождение |
| `game_ruleset_version` | Оружие, экономику, гранаты и механику конкретного игрового патча |
| `map_geometry_version` | Координаты, препятствия, навигацию и точки карты |
| `competition_rules_version` | Приглашения, регистрацию составов, форматы и тайм-ауты турнира |
| `vrs_model_version` | Конкретную официальную модель Valve и её параметры |
| `tactic_revision / replay_format_version` | План, реально использованный в матче, и формат его записи |

Созданная карьера получает собственную исходную базу и историю. Установка нового набора реальных составов предназначена для новых карьер и редактора; она не переносит реальные трансферы в уже идущую игру. Неизвестные зарплаты, потенциал и личностные качества нельзя обозначать как проверенные факты: исходный пакет хранит происхождение и статус оценки.

Динамический патч меняет конкретные конфигурации по игровому расписанию. Настройка частоты патчей сохраняется в карьере. Новый реальный документ Valve не должен незаметно переписать правила старого турнира; выбранная версия турнира и карта матча фиксируются. Уже начатое соревнование не меняет геометрию посреди серии.

### Требования к адаптеру VRS

- Проверить официальный источник и зафиксировать commit/hash, лицензию и конфигурацию используемой модели. Источники и состояние проверки находятся в `SOURCES.md`.
- Переводить фактические игровые встречи, призовые и составы в вход выбранной модели, сохраняя трассировку преобразования.
- Не использовать замену «место на турнире → фиксированные очки», средний OVR или произвольный Elo под названием VRS.
- Импортировать достаточную предысторию для выбранной стартовой даты либо честно определить альтернативный старт без полной истории. Одного снимка таблицы VRS может не хватать для дальнейшего корректного пересчёта.
- Проверять совпадение с официальным кодом на фиксированных входных наборах. Допуски округления и причины расхождений должны быть явными.
- Хранить дату рейтингового среза, по которому выданы приглашения. Текущая позиция не заменяет зафиксированный турнирный снимок.

Точные окна учёта, составы, правила преемственности и квалификации берутся из выбранной версии источника. Архитектура не закрепляет их по памяти. VRS, спортивная сила, популярность, репутация и статистический rating остаются разными вычислениями.

## 10. Сохранения и восстановление

Предлагаемый формат — отдельная SQLite-база на карьеру с необходимыми исходными данными и манифестом версий. Сохранение, загрузку и смену активной карьеры выполняет только домашний сервер через общую последовательную обработку команд. Загрузка или сброс создаёт новый контекст ревизий. Команды из вида до загрузки отклоняются, а все подключённые клиенты получают обновлённое состояние. Глобальные пользовательские настройки и необязательные секреты интеграций находятся отдельно. Карьера не должна зависеть от текущего содержимого внешнего сайта или постоянно изменяемого пакета данных.

Сохраняются не только люди и счёт: нужны модельное время, все состояния RNG, очередь событий, незаконченные переговоры, обещания, активные регистрации, состояние матча и бомбы, знания агентов, pending-команды и их идентификаторы, параметры обновлений и ссылки на закреплённые версии.

Ручное и автоматическое сохранение выполняются в согласованной точке. Для продолжающегося матча это граница завершённого тика/прикладной команды; формат должен позволять восстановить это состояние. Простая копия открытого файла БД не является проектом надёжного сохранения. Для формирования снимков доступен официальный [SQLite Online Backup API](https://www.sqlite.org/backup.html); конкретный способ реализации и поведение при ошибке проверяются интеграционно.

Новое сохранение сначала формируется отдельно, проверяется и затем становится доступным пользователю. Сбой не должен уничтожать последний успешный слот. Миграция работает с резервной копией, сохраняет историю версий и сообщает о несовместимости; молчаливое удаление полей или создание новой пустой карьеры вместо загрузки недопустимо.

Обещание совместимости должно опираться на тесты поддерживаемых версий. Детерминизм не означает, что любое старое сохранение можно пересчитать новым алгоритмом с тем же результатом. Для текущего матча требуется совместимый движок или явно проверенная миграция, а архивная визуализация должна читать зафиксированную запись.

## 11. История, статистика и воспроизведение

Счёт, убийства, ADR и другие доступные метрики выводятся из записанных действий и результатов. Для любой статистики фиксируется определение и версия формулы. Закрытые или не подтверждённые формулы внешнего сайта нельзя выдавать за точную реализацию под известным названием.

Рабочее решение для воспроизведения — запись событий и изменений отображаемого состояния с периодическими опорными кадрами. Перемотка восстанавливает состояние от ближайшего кадра; переключение скорости проигрывает запись, не проводит матч заново. Формат должен сохранять движения и эффекты, достаточные для нужной точности радара, без обязательной записи полной копии мира на каждом тике.

Для расследования и повторного headless-расчёта отдельно нужны seed, точные входы, версии и журнал команд. Эти данные полезны для воспроизводимости, но не заменяют совместимый архив просмотра при изменившемся ядре.

Уровень хранения подробной телеметрии всех фоновых матчей требуется измерить: размер сезона и скорость открытия должны попасть в отчёт. Базовая история результатов, составов и рейтингов не удаляется ради ускорения. Политика хранения подробных повторов и сам пользовательский сценарий повторов отмечаются отдельно от уже согласованной истории карьеры в `DECISIONS.md`.

## 12. Представления интерфейса и знания менеджера

Frontend получает специализированные DTO для текущего сценария. Полная внутренняя модель не отправляется браузеру с последующим сокрытием полей стилями.

Для чужого игрока API выдаёт известные диапазоны и оценку скаута, уверенность и дату отчёта; истинный потенциал и скрытые личностные параметры остаются внутри симуляции. Для матча выдаётся выбранное наблюдательское представление, а объяснения ИИ строятся из доступных ему наблюдений. Для публичной новости используется только информация, доступная её автору по правилам игрового мира.

Поток обновлений содержит контекст активного сценария или карьеры, номер последовательности и ревизию. После разрыва WebSocket клиент автоматически переподключается с задержкой между попытками, восстанавливает аутентифицированное подключение и получает актуальный авторизованный снимок с позицией в потоке. Сервер обеспечивает согласованный переход от снимка к обновлениям. Клиент пропускает уже полученные сообщения и запрашивает новый снимок при разрыве последовательности или несовпадении контекста. Пока состояние не синхронизировано, интерфейс показывает статус соединения и блокирует новые команды изменения. Команды с неизвестным исходом сверяются по идентификаторам по правилам раздела 6.

Переподключение и смена устройства сохраняют применённый прогресс и не запускают второй экземпляр матча. Симуляционное время и разрешения тренера определяются игровыми правилами на сервере. Интерполяция маркеров используется для отрисовки.

Русский интерфейс должен показывать реальные состояния загрузки, отсутствия данных, ошибки, недоступного действия и успешного применения. Видимая функция должна иметь работающий путь до изменения состояния/сохранения. Демонстрационные данные допустимы в изолированном тестовом наборе с явной маркировкой; они не подменяют незавершённый игровой функционал.

С R0 каждый реализованный сценарий поддерживает функциональный паритет на ПК, смартфонах и планшетах. Мобильная компоновка адаптирует навигацию, панели и таблицы под портретную и альбомную ориентации. Действия и сведения доступны без наведения. В матч-центре и редакторе PixiJS обрабатывает сенсорные жесты масштабирования и перемещения карты. Жест навигации не должен случайно размещать точку или изменять маршрут. Статистика, таблицы и текстовые команды остаются доступными обычными UI-компонентами. Отрисовка карты через canvas не является поводом спрятать весь матч-центр в нечитаемой картинке. Цвет игроков дополняется номером/никнеймом, состояние выбранного инструмента и недопустимые действия объясняются текстом.

## 13. LLM и локальные интеграции

Все обязательные механики работают без LLM. Рабочий вариант текстового адаптера — необязательный DeepSeek; поддержка других провайдеров возможна без изменения предметных правил, но не требует универсального провайдерного фреймворка в первом этапе.

Программная логика определяет повод, участников, доступные знания, смысл ответа и последствия. Модель может оформить реплику, интервью, новость или субъективный комментарий. Она не присылает SQL, изменения контрактов, скрытые характеристики или произвольный новый результат матча.

Без ключа, при тайм-ауте, отказе или некорректном ответе используется полноценное текстовое представление на основе шаблонов и фактов. Симуляция не блокируется ожиданием сервиса. Сгенерированный текст сохраняется, чтобы одно событие не меняло содержание при каждом открытии и не оплачивалось повторно.

Ключи не входят в репозиторий, сохранения, повторы и диагностические архивы. Внешний запрос получает только нужный контекст конкретной сцены. Платные вызовы и реальные расходные проверки не выполняются автоматически при установке, CI или запуске обычных тестов.

## 14. Доступ к домашнему серверу

- По умолчанию сервер принимает подключения только с loopback. Доступ по локальной сети и защищённый удалённый доступ включаются владельцем явно, каждый режим отдельно. Для локального браузера сохраняется проверка происхождения и контекста изменяющих запросов и WebSocket.
- Сетевой доступ требует защищённого транспорта HTTPS/WSS с проверкой подлинности сервера. Удалённое подключение может идти через явно настроенный защищённый шлюз или частную сеть. Открытие в интернет незащищённого порта игры не требуется.
- Владелец явно разрешает подключение устройства. Сервер аутентифицирует сетевого клиента для чтения состояния и отправки команд по HTTP, а также отдельно при установлении WebSocket. Сетевой клиент не получает данные до проверки. Политика допустимых origin учитывает браузеры и будущую оболочку Capacitor. Секреты подключения хранятся отдельно от сохранений и не попадают в диагностические журналы. Возможность отозвать доступ устройства сохраняется и для уже установленных соединений.
- При истечении или отзыве доступа интерфейс сообщает о необходимости подтверждения доступа. Аутентификация устройства даёт доступ к игре одного менеджера. Отдельные игровые аккаунты, роли и облачная учётная запись не требуются.

### Жизненный цикл Windows-приложения

Launcher резервирует loopback-сокет до запуска сервера, подтверждает готовность HTTP и только затем открывает браузер. Блокировка процесса и файл с адресом в пользовательском профиле позволяют второму запуску открыть тот же экземпляр. При занятом порте launcher запрашивает свободный порт у ОС. Команда завершения доступна из домашнего интерфейса. При остановке сервер завершает сетевые соединения, останавливает часы и закрывает SQLite.

Сетевые настройки доступны на loopback. По явному выбору владельца приложение открывает второй TLS-слушатель на конкретном частном IPv4. Обе точки входа используют один объект хранилища и одно условие уведомления клиентов. Часами симуляции и жизненным циклом владеет основной процесс. Сетевой слушатель не публикует операции управления домашним сервером. Его отключение завершает сетевые соединения без остановки локальной игры.

Публичный сертификат отдельного домашнего УЦ передаётся владельцем на телефон. Сервер выпускает короткоживущий сертификат с IP SAN и хранит ключи в пользовательском профиле. Доверие устанавливается владельцем устройства. Код приглашения одноразовый. QR приглашения передаёт код в URL-фрагменте, чтобы браузер не отправлял секрет в запросе страницы. Доступ к состоянию требует сопряжения и проверяется отдельно для HTTP и WebSocket.

## 15. Производительность: сначала измерение

Python выбран как исходный вариант реализации, а не гарантия выполнения полной модели мира с любым размером базы. До масштабирования необходимо измерить один полноценный матч, пакет независимых матчей и типичное продвижение календаря.

Отчёт фиксирует оборудование, версии, конфигурацию, seed/набор входов, полноту механик, время расчёта, память и объём сохранённой телеметрии. Измерение на упрощённом боевом сценарии нельзя выдавать за скорость всей карьеры.

При выявленном ограничении сначала проверяются частота ненужных вычислений, повторная навигация, запросы к БД, размер передачи данных и организация задач. Затем допустимы кэширование с корректными ключами версий, пакетные расчёты и процессы-работники. Перенос измеренного горячего участка в другой язык рассматривается только при сохранении контрактов и проверке эквивалентности результатов.

Снижение точности официального матча в фоне ради красивого benchmark нарушает продуктовую основу. Уменьшение частоты отрисовки, сжатие телеметрии и агрегированная любительская сцена относятся к другим слоям и должны называться своими именами.

## 16. Проверки, необходимые архитектуре

Проверки добавляются под конкретные механики и риски; перечень не требует запускать многолетнюю симуляцию для каждого изменения подписи кнопки.

| Риск | Проверка |
|---|---|
| Скорость просмотра влияет на исход | Один вход и команды дают одинаковый результат в headless, ×1 и ускорении |
| Сохранение теряет часть контекста | Продолжение из снимка совпадает с непрерывным расчётом, включая RNG и знания |
| Всевидящие игроки | Изменение неизвестной позиции противника не меняет решение до доступного наблюдения |
| Неограниченные тренерские коллы | Команда вне разрешённого тайм-аута отвергается также при прямом вызове API |
| Повторные операции | Повтор команды/результата не удваивает трансфер, деньги, статистику и развитие |
| Ошибочный VRS | Адаптер совпадает с закреплённой официальной моделью на одних входах |
| Утечка скаутинговой истины | DTO и диагностические пользовательские ответы не раскрывают скрытые значения |
| Патч ломает историю | Старый матч/архив открывается со своими правилами и геометрией |
| Конфликты фоновых вычислений | Изменение порядка завершения работников не меняет порядок применения результатов |
| Проблемы длительной карьеры | Пакетные сезоны проверяют составы, назначения, денежные операции, расписание и рост базы |
| Ошибки доступа | Доступ только на ПК по умолчанию. Явное включение и выключение LAN и защищённого удалённого режима. HTTP и WebSocket без действительного доступа отвергаются. Отзыв закрывает доступ устройства |
| Потеря связи или подтверждения | Автоматическое восстановление WebSocket, получение снимка и актуальных обновлений. Обрыв до и после фиксации команды, включая потерю ответа. Применённый прогресс сохраняется, эффект команды учитывается один раз |
| Конфликт устройств | Два подключённых клиента видят один мир и одни сохранения. При конкурирующем изменении устаревшая команда отклоняется. После загрузки или сброса оба клиента получают новый снимок и старые команды не применяются |
| Неиграбельный интерфейс | Playwright проверяет реальные сценарии в десктопных и мобильных разрешениях, включая смартфоны и планшеты в обеих ориентациях. Сенсорные сценарии проверяют действия и жесты карты. Скриншоты используются для визуальной проверки на каждом типе устройства |

В боевых сценариях отдельно проверяются препятствия, видимость, закупки, смерть исполнителя тактики, установка/обезвреживание бомбы, смена сторон, завершение карты и отсутствие бесконечных зависаний. Статистические проверки баланса выполняются по наборам seed и распределениям, а не по требованию победы конкретной команды в одном запуске.

Этот документ не свидетельствует о прохождении перечисленных проверок. Codex должен реализовывать и подтверждать их по этапам, а фактически выполненные команды, результаты и ограничения указывать в описании соответствующего изменения.


## 17. Контракты R3

[Спецификация R3](docs/CAREER_R3.md) обязательна. Разделить исходные пакеты, карьерное состояние и проекции знаний; режим карьеры определяет серверные полномочия, не отдельное ядро. Версионировать каталог навыков, правила расчёта, пакеты и сохранения независимо. Редактор работает с пакетами, не с активной карьерой. Очередь событий и результаты фоновых матчей применяются атомарно и идемпотентно; охват не меняет ядро. Проверять миграции активного состояния и ручных слотов из предыдущих версий, не маскировать отсутствующие поля значениями по умолчанию без обоснования.

В R3.1 реализация модели мира находится в `backend/world.py`, каталог и веса ролей — в `backend/skills.py`. Источник данных, схема, каталог, формула OVR, правила BO1 и контрольная точка имеют отдельные версии. [Связи, граница доступа и миграция](docs/WORLD_R31.md)

Редакции R3.2 находятся в таблице `data_pack` и доступны через отдельный API редактора. Команда `database-match` сохраняет локальную копию только двух пятёрок и нужных связей. Компоненты просмотра получают проекции с разрешёнными значениями. [Формат и семантика](docs/DATABASE_R32.md)

Портреты R3.2 обрабатываются отдельным потоком домашнего сервера. Собственная SQLite-библиотека хранит очередь, права, отклонения и PNG по SHA-256. Готовая внешность проецируется в игровой профиль и выбранную пятёрку. [Источники, модель и порядок работы](docs/PORTRAITS_R32.md)

R3.3 использует закреплённые редакции базы, серверную очередь выставочных встреч, общие для устройств слоты и матчевое ядро BO1. [Устройство карьеры и результаты нагрузочных прогонов](docs/CAREER_R33.md)


## Реальные карты и серии R4

Обязательные контракты и приёмка: [MAPS_R4](docs/MAPS_R4.md). Версионированная геометрия, высоты, навигация, видимость, материалы и радар используют согласованную систему координат. Карта и серия сохраняют собственные версии и состояние. Депо сохраняется для тестов и совместимости.
